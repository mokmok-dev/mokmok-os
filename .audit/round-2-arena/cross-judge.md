## Recommended base

**Candidate 2.** It is the only candidate that records the request content *before* dispatch and re‑dispatches from stored bytes (criterion 1), that makes "a retried step cannot execute twice" a return type rather than a derivation the caller must trust (criterion 4), that explicitly names the complexity hidden and denies pass‑through (criterion 3), and that keeps the kernel a pure composition root while leaving protocol/state‑machine/event‑store/artifact untouched and adding only the allowed kernel→runtime edge (criterion 5) — with the cleanest single‑shell, budget‑bounded coding‑agent surface (criterion 6). Its two costs — a second durable vocabulary and closing a budget‑exhausted session as `Completed` — are explicitly named and both fixable.

## Grafts

**From Candidate 3 (into base):**

1. Model‑call durability semantics: treat a model execution's `Unknown` as retryable (it holds no checkout reach) while a tool `Unknown` halts, as a fact of the log (c3:213, 176). This closes Candidate 2's weakest criterion‑1 spot — a model crash currently re‑asks blind via `attempt = max+1` (c2:166‑171).
2. `Environment::Exact`/`Request::inputs` (c3:192‑226) as the escape hatch if the credential is ever moved out of the trusted process; the `env_clear` observation is real (sandbox.rs:326‑334).

**From Candidate 1 (into base):**

1. The `Log::verify` rule that a content record cannot float free of its machine fact — a `Prompt`/`Answer`/`Call`/`Observation` admitted only alongside (or after) the `ModelRequested`/`ModelAnswered`/`ToolRequested` it belongs to (c1:99‑104). This hardens Candidate 2's `Record::apply` beyond content‑keying alone.
2. Route the provider's traffic through `mokmok-egress` for destination validation and an audit row (c1:190‑192), against Candidate 2's raw `reqwest` (c2:235–237).

## Claims the code contradicts

1. **Candidate 3, c3:214 (and c3:185): "carries a fresh `CommandId`, so a re-issued identical append is the store's `Replayed`."** The store's replay is keyed on the *command id*: `Outcome::Replayed` only fires for the same `CommandId` (db.rs:10‑11; slice.rs:145‑148 — "reusing this submit's id would make the second append a replay"). A **fresh** `CommandId` plus `Expected::At(version)` yields `Conflicted` (or a new commit), never `Replayed`. The mechanism Candidate 3 names cannot produce the idempotence it claims; the actual guard is `next` re‑deriving from the view plus `TurnOver`/`ResolutionConflict`.
2. **Candidate 2, c2:78 — `Step { … pub notice: Notice }` while c2:97‑98 claims "Every type on these ports is the runtime's own" and c2:233 says the runtime takes "no … kernel."** `Notice` is the kernel's type (slice.rs:59), and §5.12 forbids any lower crate depending on `mokmok-kernel` (architecture.md:306), so a runtime type cannot embed it; the runtime's module map (c2:40) defines no `Notice`. As sketched, `Step` either leaks a kernel type or references an undefined one.

No candidate adds a dependency edge forbidden by the §6 table (architecture.md:312‑323); all new edges run top‑down (kernel→runtime, runtime→provider/ports).
